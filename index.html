Validation pipeline

Language-aware parsers are used when available. The structural fallback checks delimiters only and is explicitly marked as limited.

flowchart TD
  A[Editor input] --> B{Input size valid?}
  B -- No --> E[Show input-limit error]
  B -- Yes --> C{Language capability}
  C -- Parser available --> D[Parse / prepare]
  C -- Partial only --> F[Lexical structure scan]
  D --> G[Normalize diagnostics]
  F --> G
  G --> H[Accessible result panel]

Application architecture

UI dependencies are optional. If a CDN or parser fails, the app reports the missing capability instead of implying a successful full syntax check.

flowchart LR
  UI[Single index.html] --> SAFE[Size and capability guard]
  SAFE --> PARSERS[On-demand browser parsers]
  PARSERS --> RESULT[Normalized issues]
  SAFE --> BASIC[Structural fallback]
  BASIC --> RESULT
  PARSERS -. dependency failure .-> WARN[Clear unavailable message]
  WARN --> RESULT
  UI <--> LOCAL[Opt-in LocalStorage draft]

The application does not run user-submitted code. A clean parse is not a guarantee of runtime correctness or security. Mermaid diagram rendering requires network access.

Error-handling workflow

Unsupported languages, invalid source, unavailable parsers, and oversized inputs produce clear results instead of a success-shaped fallback.

flowchart TD
  A[Validation request] --> B{Input within size limit?}
  B -- No --> C[Report size limit]
  B -- Yes --> D{Language parser available?}
  D -- Yes --> E[Parse without executing source]
  D -- No --> F{Structural fallback appropriate?}
  F -- Yes --> G[Run limited delimiter checks]
  F -- No --> H[Report validator unavailable]
  E --> I[Show findings and capability limits]
  G --> I
  C --> I
  H --> I
Single-file app · Dependencies load from external CDNs · Never save passwords, tokens, private keys, or confidential source code to LocalStorage.
